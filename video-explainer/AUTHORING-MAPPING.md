# The Mapping deck — authoring & rebuild

A second slide deck, focused **entirely on the OCF→Carta mapping** and the properties left behind as
**candidate community extensions**. It's a sibling of the OCF Core explainer deck — same design system,
same SVG→PPTX pipeline — but a different generator and story. This is the PPTX companion; for the
shared build mechanics (fonts, the three deck flavors, "fully editable", gotchas) see
[`AUTHORING-PPTX.md`](AUTHORING-PPTX.md).

---

## What it is

`gen_mapping.py` is the source of truth (it imports every drawing primitive from `gen.py`, so the two
decks share one visual language). It produces **41 slides**:

| Section | Slides | Content |
| --- | --- | --- |
| **Title** | 1 | OCF Core — The Mapping |
| **§1 Philosophy** | 3 | derive-don't-declare · the field rule (value-loss OK, existence-loss not) · strict vs. rich |
| **§2 Convention** | 3 | the `.mapping.md` DSL & kind verbs · the three-bucket type test · polymorphic & composite routing |
| **§2.5 Schema mechanism** | 3 | OCF is JSON Schema (strict, `additionalProperties:false`) · a Carta object's shape · the named `OCF-Extended-…` extension schema (`allOf` Core + only the catalogued props, still strict — **not** a blanket `additionalProperties:true`) |
| **§3 Gaps** | 2 | the four loss types · the marquee OCF gaps (phantom/PIU, exercise cash & tax, acceleration, interest) |
| **§4 Matrix** | 1 | every Core object, mapped-vs-left-behind at a glance |
| **Full examples** | 3 | worked deep-dives (Issuer · Stakeholder · StockClass): the whole OCF object → what lands in Carta → a hypothetical `*Extension` object carrying the dropped properties |
| **§4 Objects** | 24 | one slide per admissible Core object — the extension candidates, both directions |
| **Close** | 1 | the candidates are on the table |

Each **per-object slide** has two panels — **OCF has it** (green: OCF-native, no Carta home) and
**Carta has it** (blue: Carta-only, OCF doesn't model it) — feeding a gold **community-extension**
target. Within each panel: a **ratio bar** (mapped vs. left behind), the **candidate** list (gold, the
hero; OCF-required casualties flagged), and a dim **ALSO MAPPED** line for context.

## Where the data comes from (synthesized, not recomputed)

The deck **does not re-run the analysis** — it synthesizes the committed, generated inventories:

| Deck content | Source doc |
| --- | --- |
| OCF-side left-behind (`ocf_left`, with required flags) | `core/core-gaps.md` §(a) |
| what lands (`ocf_mapped` / `carta_mapped`) | `docs/generated/mapping-inverse-report.md` and the mapping-flow gallery (canonical target-first evidence) |
| Carta-side concepts (`carta_left`) | canonical inverse report empty-slot panels plus `core-rich/core-gaps.md` inverse candidates, de-noised into concept labels |
| the marquee OCF gaps (§3) | `core/core-gaps.md` §(b3) "true gaps" |
| the full examples (whole object + kind per field) | the object's `objects/*.mapping.md` `fields:` block (`EXAMPLES` in `gen_mapping.py`) |

Left-behind is **collapsed across polymorphic variants**: a field that lands in *any* variant is not
"left behind" (matches the canonical target-first report's mapped target evidence). The mechanical field
lists live in `COMPUTED` in `gen_mapping.py`; the prose (roles, takeaways, `carta_left` concept labels)
is authored in `OBJECTS`.

> **Refreshing after a mapping change:** regenerate the inventories (`npm run core:build && npm run mapping:artifacts`),
> then re-derive the embedded lists. A helper isn't checked in — the `COMPUTED` block was generated by
> parsing `core-gaps.md` §(a) (minus mapped-in-any-variant) and the canonical inverse target evidence. If a
> deferred mapping (`defer:`) becomes real, its fields move from a `carta_left` candidate to `carta_mapped`.

## Rebuild

Needs `python-pptx` (a scratch venv is fine — `.pptxenv/` alongside) and, for the image/editable
flavors, `rsvg-convert`. From this folder:

```sh
# 1. stills (shapes + text) — the only input the NATIVE deck needs
python3 gen_mapping.py stills map_stills

# 2. fully-editable NATIVE deck (every element a native PowerPoint object, no images)
DECK_GEN=gen_mapping.py DECK_STILLS=map_stills DECK_OUT=ocf-core-mapping \
  python3 build_pptx_native.py                      # → ocf-core-mapping-native.pptx

# 3. (optional) editable-text + image flavors — need rasterized plates/slides
python3 gen_mapping.py plates map_plates
i=1; for nm in $(python3 gen_mapping.py manifest | awk '$1!="TOTAL"{print $1}'); do
  rsvg-convert -w 2560 -h 1440 "map_plates/$nm.svg" -o "map_plate_png/$(printf %02d $i)_$nm.png"
  rsvg-convert -w 2560 -h 1440 "map_stills/$nm.svg"  -o "map_slides/$(printf %02d $i)_$nm.png"
  i=$((i+1)); done
DECK_GEN=gen_mapping.py DECK_STILLS=map_stills DECK_PLATES=map_plate_png DECK_OUT=ocf-core-mapping \
  python3 build_pptx_editable.py                    # → ocf-core-mapping-editable.pptx
DECK_SLIDES=map_slides DECK_OUT=ocf-core-mapping \
  python3 build_pptx.py                             # → ocf-core-mapping.pptx
```

The three builders are shared with the explainer deck and are **backward-compatible**: with no `DECK_*`
env vars they build the original `ocf-core-explainer*` decks exactly as before.

## Files

| File | Role |
| --- | --- |
| `gen_mapping.py` | the mapping deck's source (scenes + embedded `OBJECTS`/`COMPUTED` data; imports primitives from `gen.py`) |
| `ocf-core-mapping-native.pptx` | fully-native deck (every element editable, no images) — **use this to edit** |
| `ocf-core-mapping-editable.pptx` | editable-text over styled plates |
| `ocf-core-mapping.pptx` | pixel-perfect image deck |
| `build_pptx*.py` | shared builders (env-parameterized; default to the explainer deck) |

**Caveat (same as the explainer deck):** there's no headless PowerPoint/LibreOffice renderer on the
build machine, so the decks are verified structurally but the final render should get a quick eyeball
in PowerPoint. Keep **Helvetica Neue** and **Menlo** installed.
