# OCF Mapping Skeleton Generator — Design

**Date:** 2026-05-18
**Status:** Draft, pending implementation
**Repo:** this one (`~/Code/OCF-Composed-Schemas/`)

## Goal

Generate one `.mapping.md` file per OCF object and type, sitting next to its
`.schema.json`, pre-populated with a YAML mapping skeleton. The skeleton makes
filling in a field-by-field mapping to some other JSON-Schema-based standard a
mechanical, fill-in-the-blank task for a human (or AI assistant).

The format is **doc-first, parseable later**: humans read and edit the markdown
directly; the YAML mapping block is regular enough that a future script could
extract it for codegen or validation without changing the authored content.

## Context

This repo holds:

- **Composed OCF schemas** under `objects/`, `types/`, `enums/`, `primitives/`,
  `files/` — 175 files generated by `npm run schema:compose` in the
  `Open-Cap-Format-OCF` repo (see PR #576), with each `allOf` ancestor chain
  flattened into a self-contained schema.
- **(this spec adds)** A `mapping:skeleton` generator that emits sibling
  `.mapping.md` files next to each `.schema.json` in `objects/` and `types/`.

The mappings document OCF → some other JSON-Schema-based standard. The target
standard is not yet fixed; each `.mapping.md` records its target in
frontmatter (`target_standard`, `target_version`) so different files can map to
different targets if needed.

## In scope

- File layout: sibling `.mapping.md` next to each `.schema.json` in `objects/`
  and `types/` only. Not generated for `enums/`, `primitives/`, `files/` —
  those are referenced *from* mappings (as `values:` entries) but don't get
  their own mapping documents.
- Markdown template (frontmatter + body sections).
- Mapping YAML block schema and pre-population rules.
- Generator CLI: input is this repo's tree; output is the same tree with
  `.mapping.md` siblings created (or, with `--force`, regenerated).

## Out of scope

- Executing or validating filled-in mappings.
- Bidirectional (target → OCF) mappings.
- Refreshing composed schemas from upstream OCF (that's `npm run schema:compose`
  in the OCF repo).
- The mapping consumer (codegen, transformer, validator).
- Auto-recomputing `coverage:` from filled-in entries — a future script can
  do this; the generator only sets the initial `0/N`.

## Markdown template

Each generated `.mapping.md` has the structure below. Concrete values come
from the corresponding composed schema.

### Frontmatter

```yaml
---
ocf_schema_id: <string, the schema's $id>
ocf_object_type: <string const if properties.object_type.const exists, else null>
ocf_title: <string, the schema's title>
ocf_kind: object   # or 'type'
required_fields:
  - <string>       # in the order they appear in the composed required[] array
target_standard: TBD
target_version: TBD
status: draft      # draft | partial | complete | reviewed
last_generated: 2026-05-18   # ISO 8601 calendar date (YYYY-MM-DD)
---
```

### Body sections

1. **Heading.** `# {ocf_title} → {target_standard}` — when
   `target_standard` is still `TBD`, the literal string `TBD` appears in the
   heading; the author updates the heading when they fill in the frontmatter.
2. **Description blockquote.** The schema's `description` field rendered as a
   single Markdown blockquote (`> ...`). If the schema has no description,
   render `> _(no description in source schema)_`.
3. **OCF schema section.** A `## OCF schema` heading, a markdown link to the
   sibling `.schema.json` for easy navigation, then a collapsible `<details>`
   block containing the composed schema pretty-printed (2-space indent) inside
   a ` ```json ` fence.
4. **Mapping section.** A `## Mapping` heading followed by the YAML block
   defined below (also in a ` ```yaml ` fence).
5. **Notes section.** A `## Notes / open questions` heading followed by a
   single empty bullet (`- `).

### Mapping YAML block — schema

```yaml
status: draft       # draft | partial | complete | reviewed
coverage: 0/N        # N = total field count, filled-in count starts at 0

fields:
  <property_name>:
    kind: <kind>     # see vocabulary below
    target: <string | [string, ...] | null>   # JSONPath in target, or array for split, or null for unmappable
    values:                                   # only present for enum-typed properties
      <OCF value>: <target value or TODO>
    transform: |                              # only for split / combine / computed
      <free-form prose or pseudocode>
    notes: <string>                           # optional, free-form
```

### `kind` vocabulary (controlled)

| `kind`         | Meaning                                                                                         | `target` shape         |
| -------------- | ----------------------------------------------------------------------------------------------- | ---------------------- |
| `rename`       | 1:1, path-only change (including type-compatible renames)                                       | `string`               |
| `split`        | One OCF field maps to multiple target fields                                                    | `[string, string, ...]` |
| `combine`      | Multiple OCF fields collapse into one; primary entry references the others in `transform`      | `string`               |
| `enum-remap`   | Value-by-value mapping; `values:` block is required                                             | `string`               |
| `computed`     | Derived from other OCF fields and/or context; `transform:` describes how                        | `string`               |
| `unmappable`   | Target has no equivalent                                                                        | `null`                 |
| `TODO`         | Placeholder pre-filled by the generator; means "author has not chosen yet"                      | `TODO`                 |

`kind: TODO` is the only kind the generator ever emits. The author selects a
real kind during fill-in.

## Pre-population rules

For each `.schema.json` in `objects/` or `types/`, the generator:

1. **Frontmatter values** are pulled directly from the schema:
   - `ocf_schema_id` ← `$id`
   - `ocf_object_type` ← `properties.object_type.const` (else `null`)
   - `ocf_title` ← `title`
   - `ocf_kind` ← `object` if file is under `objects/`, else `type`
   - `required_fields` ← `required` array, in source order
2. **Description blockquote** ← `description` (or the no-description fallback
   sentence).
3. **Embedded schema** is the source `.schema.json` JSON, pretty-printed with
   2-space indent.
4. **Mapping `fields:`** is built by walking `properties` in the order they
   appear in the composed JSON. For each property:
   - Emit `kind: TODO`, `target: TODO`.
   - If the property is enum-valued (see Enum detection), also emit a
     `values:` map with every OCF enum value as a key, each mapped to `TODO`.

### Enum detection

A property is "enum-valued" if any of these holds, after resolving `$ref`s
against the in-memory registry:

- The property JSON has an inline `enum` array.
- The property JSON has a `const`.
- The property JSON has `$ref` pointing to a schema whose top level has an
  `enum` array.
- The property JSON is `{ type: "array", items: <enum-ish> }` — same rules
  recursively. The `values:` map still pre-populates from the items' enum.

For `properties.object_type` (which uses `const`), the resulting `values:`
map has exactly one key — useful for targets that re-encode object kind.

### What the generator does NOT expand

References to non-enum object types (e.g.,
`share_price: { $ref: ".../Monetary.schema.json" }`) are **not** expanded. The
author writes the target path; the referenced type's own `.mapping.md`
captures its internal mapping. This keeps each file scoped to a single OCF
type and avoids combinatorial explosion.

## Schema registry

The generator builds an `$id → composed-schema` registry by reading every
`.schema.json` under `enums/`, `primitives/`, `types/`, `objects/`, `files/`
at startup. This is needed solely for enum detection via `$ref`. The registry
is in-memory; the generator does not write to anything outside the target
output paths.

## Generator CLI

A new script, `scripts/generate-mapping-skeletons.ts`, exposed as:

```
npm run mapping:skeleton -- [--force] [--dry-run] [--filter <glob>] [--verbose]
```

Flags:

| Flag         | Default | Meaning                                                                                   |
| ------------ | ------- | ----------------------------------------------------------------------------------------- |
| `--force`    | off     | Overwrite existing `.mapping.md` files. Updates `last_generated`; replaces body wholesale. |
| `--dry-run`  | off     | Print which files would be written; write nothing.                                        |
| `--filter`   | none    | Glob (relative to repo root) restricting which `.schema.json` files are processed.        |
| `--verbose`  | off     | Per-file progress to stdout.                                                              |

### Behavioral invariants

- **Idempotency.** Running with no flags after a prior run is a no-op
  (existing files are skipped). Running with `--force` against an unchanged
  source schema regenerates byte-identical content **except** for the
  `last_generated` line.
- **Authoring safety.** Without `--force`, the generator never overwrites a
  file. If an author has edited a `.mapping.md`, their work is preserved.
- **Failure mode.** If any source `.schema.json` cannot be parsed, the
  generator prints the offending path and exits non-zero before writing
  anything.

repo's conventions where reasonable:

- `.prettierrc` matching OCF's settings.

## Testing

The generator script has unit tests covering at minimum:

- Skeleton rendering for a property-only object (no enums).
- Enum pre-population for an inline `enum:` property.
- Enum pre-population via `$ref` to a schema in `enums/`.
- `object_type.const` rendered as a single-key `values:` map.
- Array-of-enum properties (`items.enum`).
- `required_fields` frontmatter ordering matches source `required[]`.
- Schemas without `description` get the fallback sentence.
- Idempotency: running twice writes once.
- `--force` overwrites and bumps `last_generated`.
- `--filter` glob restricts output set.
- `--dry-run` writes nothing.
- Invalid source schema (e.g., missing `$id`) aborts non-zero before writing.

## Future considerations (deliberately deferred)

- **Coverage auto-recalc.** A separate `mapping:coverage` script that reads
  each `.mapping.md`, counts non-`TODO` `kind` entries, and rewrites the
  `coverage:` line in place. Not implemented now to keep the generator
  simple; the initial `0/N` is just a hint.
- **Cross-mapping linting.** Warn if the same target path appears in two
  files (suggests collision or accidental duplication).
- **Round-trip generator.** Synthesize a target-standard JSON Schema from a
  fully filled-in set of mappings.
- **Multi-target support.** If a single OCF schema needs to map to several
  target standards in parallel, the current "one file per OCF schema"
  layout would extend to `.mapping.{target}.md` siblings. Not modeled now.
- **Drift detection.** A check (e.g., a CI step) that flags when a source
  `.schema.json` has changed shape since `last_generated` and the
  `.mapping.md` may need re-skeletoning.
